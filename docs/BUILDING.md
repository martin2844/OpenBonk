# Source and build status

The experimental `tools/prepare-partial-fast-comparison.py` prepares private
per-mip fixtures for `tools/run-texture-native-comparison.py`, using named
textures in a local partial-conversion template and compatible Steam data.
On a Retroid Pocket 5, the ARM64 converter reproduced all 36 UnityPy fast
encoder outputs exactly for Cactus, BossPortalNormal, FBX_Log0_Color_Normal,
Bullseye_0 and t_chest_normal (26 BC1-to-ETC2 RGB, one BC3-to-ETC2 RGBA,
and nine RGBA-to-ETC2 RGBA mips). The checked-in fixture generator reproduced
the initial private study byte for byte. This confirms those particular encoder
results, not other textures, platforms or visual quality. The experimental
`--partial-etc2-fast` build option selects the fast encoder only where it
recovers more identical nonzero bytes than the quality encoder; it requires
`--partial-etc2`. In a local Linux-data study, this masked 9,988 additional
bytes and the plan restored all 1,072 archive entries exactly on a Retroid
Pocket 5. A separate Windows-data plan restored the same number of entries
on both the host and that Retroid. These are partial-stage checks, not complete launcher builds or
gameplay tests. The template still contains game-derived data; inputs and
fixtures must remain private.

The additional experimental `--partial-etc2-blend` option requires
`--partial-etc2-fast` and chooses the exact matching encoder separately for
each 16-byte output block. A private study using the prior local runtime
recovered 20,398 additional nonzero texture bytes compared with fast selection
per texture. Both Linux and Windows plans restored all 1,072 archive entries
exactly on a Retroid Pocket 5. A combined APK assembled from those plans and
previously generated intermediates passed an independent check with both ZIPs.
The same Retroid imported the Linux ZIP, produced the expected OBB hash and
entered a short Forest run with Fox and enemy defeats. Its inline texture audit
found 164,507 nonzero bytes in the measured template; other data types were not
covered by that audit. This does not prove a clean end-to-end build, Windows ZIP
import through the combined APK, complete gameplay parity or suitability for
distribution. The APK and local inputs remain private.

The experimental `--partial-etc2-byte` option requires `--partial-etc2-blend`
and selects between the two encoders for each output byte. In a private study
using the same prior runtime and local inputs, this recovered another 8,984
exact nonzero texture bytes compared with block selection. Linux and Windows
plans each restored all 1,072 archive entries on a Retroid Pocket 5; an
independent check of a combined APK restored its expected OBB from both ZIPs.
The Retroid imported the Linux ZIP through that APK, produced the expected OBB
hash, reached level one in a short Forest run, selected an upgrade and resumed.
The Linux inline texture audit found 155,523 nonzero payload bytes and did not
cover other data types. This reused prior build intermediates; it does not prove
a fresh end-to-end build, Windows ZIP import through that APK, complete gameplay
parity or suitability for distribution. The APK and inputs remain private.

The experimental `--normal-block-fallback` option requires `--normal-fallback`
and `--partial-etc2-byte`. For three known ETC2 RGB normal maps, it tries the
fast and quality Steam-derived encoders separately for each 4×4 block and
only substitutes a changed block when every decoded normal direction stays
within 10 degrees of the existing image. An unchanged encoded block is kept
even if its decoded vector is degenerate; blocks for which neither candidate
passes stay byte-identical. Linux and Windows local studies produced matching
converted OBB hashes, with 11,437 eligible and 856 preserved unsafe blocks.
The selected images are approximations, not byte-identical reconstructions.
The measured angle bound does not prove equivalent in-game shading; the stage
and any resulting APK must remain private pending further validation.

The experimental `--color-block-fallback` option requires `--partial-etc2-byte`.
Its initial version handled the specifically identified `FBX_Barrel_Color` and
`t_birdo_blue` textures, selecting a Steam source only when it was unambiguous under the
existing metadata or partial-byte checks. For every substituted 4×4 block,
the decoded candidate must satisfy both the quality and alpha/visible-pixel
limits; unsafe blocks stay byte-identical. The option rejects missing,
duplicate or incompatible named textures and is not a general color-texture conversion. In local
Linux and Windows studies, both produced the same converted OBB; focused
partial plans recovered 14,443 nonzero bytes in those textures, 2,906 more
than before substitution. On a Retroid Pocket 5, each focused plan restored
all 1,072 expected entries from its respective Steam ZIP. These are bounded
approximations, not pixel-identical textures; the complete launcher, rendering
and all game content were not tested with this option. The output remains
private and still contains game data.

## Layout

- `unity/OpenBonk/Assets/Scripts/` — reconstructed C# game and Android integration scripts.
- `unity/OpenBonk/Assets/AndroidSplitLauncher/` — Android launcher, Steam ZIP import, profiles and mods.
- `unity/OpenBonk/Assets/AndroidModPicker/` — Android mod picker integration.
- `unity/OpenBonk/Assets/Editor/` — editor tooling and diagnostic scripts; some require omitted assets or local inputs.
- `unity/OpenBonk/Assets/Shader/` — available reconstructed shader sources and metadata; provenance varies.
- `native/lua/` — Lua bridge, Lua 5.4.9 source archive, smoke test and example packages.
- `native/stable-zlib/`, `tools/`, `analysis/data-conversion/` — native support and experimental preparation, validation and reconstruction tools. Many research scripts depend on local generated intermediates and are not standalone build commands.
- `mods/` — example Lua mods and the experimental Pikachu package.

The local runtime work used Unity 2023.2.22f1 and Android ARM64. Reconstructing a working project also requires the appropriate Unity Android toolchain, compatible game data and unresolved third-party components. No personal Steam data, saves or signing keys are included. Reproducible clean setup, dependency provenance and licensing remain work to do.

One historical split-build experiment used two Unity passes and repaired the APK's OBB digest after matching the second pass's Unity GUID. `analysis/port-inventory/repair-split-guid-probe.py` accepts a directory containing `first.obb`, `second.obb` and `second.apk`, plus a new output directory. Its `--android-player`, `--build-tools`, `--java-home`, `--debug-keystore` and `--runner` options allow those local tools to be configured; `--runner none` invokes them directly. It signs with standard Android debug-key credentials. A local run on the historical inputs reproduced the historical repaired APK and OBB byte for byte using the original debug key, both with `steam-run` and with the wrapper disabled inside that environment. A different key changes the APK signature and digest. This only verifies the repair step: the two Unity passes and their historical inputs are still prerequisites, and this does not establish a clean or distributable build.

## Isolated Unity workspace

To include the Steam export in the experimental local build, use:

```sh
python3 tools/build-local-from-steam.py \
  --game /path/to/Steam/steamapps/common/Megabonk \
  --assetripper /path/to/AssetRipper.GUI.Free \
  --unity /path/to/Unity/2023.2.22f1/Editor/Unity \
  --output /path/to/new-local-build \
  --application-id com.example.openbonktest
```

This builds the Lua bridge with Unity's Android NDK, then runs the export and local Unity build described below. Alternatively, supply `--lua-library /path/to/libmegabonk_lua.so` to use a locally built bridge.
