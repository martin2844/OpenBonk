# Spawn Tracker feasibility study

The [SpawnTracker package](https://thunderstore.io/c/megabonk/p/Antiparty/SpawnTracker/) describes a live bottom-left overlay with total and unopened chests, visible only after chests spawn. Shrine and ShadyGuy spawn events, and vendor use/disappearance, are logged. It has no configuration. No source license was identified; an independent implementation must not copy its code or assets. The upstream DLL has not been run or inspected, so its exact counting rules are unknown.

OpenBonk already maintains `InteractablesStatus` for shrine information and achievements. It is attractive for a prototype but is not yet evidence of equivalent chest counts:

- `BaseInteractable.Start` only reports objects whose `ShowInDebug()` is true; chest reporting depends on the serialized `isShownInDebug` flag. Some chest prefabs or dynamically created objects may be omitted.
- `InteractablesStatus.OnInteractableUse` counts successful interactions, not unique opened chest objects. A key can keep an opened chest alive for reuse, so `numUsed` can exceed the number spawned. Blind subtraction can report an invalid number.
- Its tracking starts during initialization and resets at map generation; crypt counters are removed on dungeon exit. A new observer must define map transitions, resumed/reused objects, deactivation and destruction, and not interfere with the achievement counters.
- A chest's `A_ChestOpened` event has no instance argument; observing exact identities needs another hook at the instance interaction boundary. `OnDisable` distinguishes `opening`, and interactions can fail or throw, so tests must cover unsuccessful interactions, surviving keys, duplicate callbacks, chest window timing and transitions.
- ShadyGuy has an instance-bearing completion event. Its disappearance can be a parent destruction; a spawn/disable registry must not conflate that with a successful purchase. Shrine variants have different lifecycles, so logging needs explicit event semantics.

A shared, read-only world observation registry could track live instances without polling the scene each frame and publish bounded counts/events to an opt-in Lua policy. Use object identity and event subscriptions with cleanup; define which session/stage counts reset and whether a preserved chest is still unopened. Overlay placement must avoid touch controls and be tested in multiple resolutions and with edit mode. Test play/paused state, map and dungeon transitions, disabled behavior, lifecycle churn, no duplicate event delivery and overhead before making any parity claim. This is design research only: no host hook, package or catalog entry is available yet.
